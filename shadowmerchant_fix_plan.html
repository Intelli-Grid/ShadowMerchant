Priority 1 — critical (fix this week)
P1
Scrapers for Amazon / Flipkart / Croma are failing or returning wrong categories
Verified: Electronics page shows Amazon stationery (undated planners, diaries). The category classifier is matching on price/discount signals instead of product taxonomy — or the scraper is pulling a generic "deals" endpoint and misrouting results.
Flipkart, Meesho, TataCliq have zero products anywhere on the site right now — scrapers are silently swallowing failures.
Admitad verification tag present (meta-verify-admitad), suggesting affiliate tracking is at least partially set up, so suppression for monetisation is less likely than a scraper failure.
Fix A — add scraper health logging. Each scraper run must emit a structured log: { store, status, itemsFound, errors, timestamp }. Send to a simple endpoint or even a Telegram bot so you know the moment a scraper dies.

Fix B — rotate User-Agent + add Playwright for JS-rendered pages. Amazon and Flipkart render prices client-side. A raw HTTP fetch returns empty price nodes. Use playwright with a headed Chromium profile and a random UA per session. For Flipkart specifically, the __NEXT_DATA__ JSON blob in the page source often contains structured product data — parse that instead of DOM scraping.

Fix C — fix category routing. Add a required category_hint field to each scraper target (e.g. amazon.in/deals/electronics → "electronics"). Validate the inferred category against the hint before inserting; reject mismatches. A planner is not an electronic.
P1
Cron jobs are hanging — "Scanning" never resolves
Electronics, Gaming, Toys, Automotive, Travel, Grocery categories all show "Scanning" with no results. A cron that hangs and holds the "scanning" DB flag is worse than one that fails — it makes the site look perpetually broken.
Fix — implement job timeouts and a dead-man switch. Every cron run must: (1) set a scan_started_at timestamp; (2) enforce a hard timeout (e.g. 90s); (3) on completion OR timeout, clear the flag and write scan_completed_at. Add a watchdog query: if scan_started_at is older than 10 minutes and scan_completed_at is null, force-clear the flag and alert. Never leave a category stuck in scanning state across a page load.
P1
Low-score deals (Score < 50) appearing as homepage featured content
Verified: "New Today" leads with Score 47, 46, 41. "Trending Now" top item is Score 57. The platform's brand promise is finding real savings — featuring "Fair" and "Low" deals at the top directly contradicts this.
Fix — enforce a homepage minimum score filter in the feed query. In whatever query populates /deals/feed (Mongo, Postgres, or a Redis sorted set), add a hard WHERE shadow_score >= 55 (or equivalent) for homepage slots. "Fair" (50–64) deals belong in category pages and search results only. "Good" (65+) and "Great" (80+) are your hero products. The Kalista Saree (88% off, Score 64) should already be near the top — it just gets buried under low-score lipsticks.
Priority 2 — important (fix this sprint)
P2
No provider diversity cap — Nykaa dominates 100% of homepage
The homepage promises "8 platforms, one honest feed" but delivers one. Even if scrapers are failing, showing a single-provider feed without a label is a trust problem for new users.
Fix A — implement a provider cap in the feed selector. When building the homepage feed, bucket deals by store_id and enforce a max of 40% per store. If fewer than 3 stores have data, show a banner: "Some stores are temporarily unavailable — showing best available deals."

Fix B — fallback label when feed is single-source. If the cap can't be met (because other scrapers are down), show a small notice: "Showing Nykaa deals — Amazon & Flipkart feeds updating." Honesty builds trust.
P2
Stale deals (9–10h old) pinned at the top of "Trending"
Flash sales in India (Big Billion Days, Myntra End of Reason Sale style flash slots) expire in 2–6 hours. A 10-hour-old deal is statistically expired. The UI even says "worth a quick check" which reads as uncertain.
Fix — time-decay the feed score. Multiply Shadow Score by a freshness factor: deals under 2h = 1.0×, 2–6h = 0.85×, 6–12h = 0.65×, 12h+ = 0.4×. Sort by this adjusted score. Old deals will naturally drop below newer ones. Also implement a background job that re-validates deal links older than 6h and marks them expired if the price has changed.
P2
"Scanning" UI state misleads users
The word "Scanning" implies a live, imminent result — but these categories have been scanning for days. It creates an expectation that is never met.
Fix — replace "Scanning" with honest empty states. Three states to handle: (1) Last scanned > 24h ago, no results → "No high-value deals found recently. Check back later." (2) Scraper currently running, <5 min → "Scanning now…" with an auto-refresh. (3) Scraper failed → hide the category card entirely or show "Temporarily unavailable." Never show "Scanning" for more than 5 minutes without a timeout.
Priority 3 — polish (next cycle)
P3
Search queries only the existing DB — no real-time fetch fallback
If a user searches "Samsung Galaxy" and scrapers haven't run, they get zero results — even though deals exist on Amazon. The search bar should trigger a targeted scrape if the DB returns 0 results and the query matches a product category keyword.
Fix — add a POST /api/search/live endpoint that accepts a query, fires a targeted scraper (e.g. Amazon product search API or a headless Playwright fetch), and streams results back. Cache results for 15 minutes per query to avoid hammering sources.
P3
Category pages lack "last updated" timestamps per store
Users can't tell which store's data is fresh. A small "Amazon · updated 4m ago" label next to the store filter pill would restore confidence and set expectations correctly.
Fix — expose a GET /api/scraper/status endpoint that returns { store, last_run, items_found, status }. The frontend reads this on page load and renders a freshness indicator next to each store badge. Green = <30m, amber = 30m–3h, red = >3h or failed.
P3
Deal of the Day score is only 64 — hero deals should be 80+
The Kalista Saree (88% off) is a strong pick visually but its Shadow Score is 64 ("Good"). With a better scraper pipeline pulling high-discount electronics and fashion, DoTD should consistently come from the 80–100 band. Until then, consider a manual pin mechanism.
Fix — add a is_pinned boolean to the deals schema. Build a simple admin page (even password-protected static HTML + a single API endpoint) to manually pin a deal as DoTD. Run a nightly cron that picks the highest-scoring deal from the last 24h as a candidate, sends it to your Telegram/WhatsApp for human approval, and pins it if approved within 2h.
